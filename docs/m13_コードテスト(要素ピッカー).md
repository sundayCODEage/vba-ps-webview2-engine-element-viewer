🚀 **概要** (Overview)<br>
モダンなWebシステム（SPAや複雑なフレームワーク）を自動化するため、VBAとPowerShell（WebView2 / CDP）を非同期通信で連携させた汎用RPA操作エンジンのコアモジュールです。<br>
単なるDOM解析にとどまらず、OSレベルの **UIAutomation (UIA)** とブラウザ内部の **Chrome DevTools Protocol (CDP)** をシームレスに統合。画面上のクリック位置から、多段iframeやShadow DOMを貫通して一意のCSSセレクタ（またはXPath）を動的に逆算・生成する「ハイブリッド要素ピッカー」です。

✨ **主要機能** (Key Features)<br>

🛡️ **1. Robust DOM（レスポンシブ非表示罠の完全回避）**<br>
Webサイトで多用される「透明化された本来の入力要素」や、裏側に隠れている「スマホ用の非表示メニュー」の誤爆を防ぎます。

* **フェーズ1 (セレクタ逆生成):** 曖昧な指定（例: **//a\[contains(., 'ニュース')]**）から、画面に見えている要素だけを抽出し、優先度に従って一意のCSSセレクタを動的生成します。
* **フェーズ2 (安全なクリック - SafeClick):** 単純な **display: none** だけでなく、CSSの透明度や要素サイズを総合的に評価。対象要素を確実に画面中央へスクロール（**scrollIntoView**）させ、他の要素の裏に隠れていないか最終確認してからネイティブクリックを発火します。

🎯 **2. セレクタの自動安定性テスト** (Flakyテスト防止)<br>
ピッカーで取得したセレクタが、動的ID（**ext-gen-** 等）や仮想DOMの再描画によって短時間で消滅・変化しないか（一過性の幻ではないか）をエンジン内部で複数回自動検証します。これにより、RPA本番稼働時の「要素が見つからない」エラーを未然に防ぎます。

👻 **3. 多段iframe & Shadow DOMの完全透過**<br>
クロスドメイン制約（CORS）を考慮しつつ、複雑にネストされた **iframe** や、Web Componentsの **Shadow DOM** 内部にカプセル化された要素に対しても、物理座標から直接ドリルダウンして要素を特定します。

🔍 **4. 通信負荷ゼロで実現する高速Fuzzy検索**<br>
IDやName属性を持たない要素（単なる `<a>` や `<span>` タグ）を特定する際、画面上の表示テキスト（**innerText**）が重要な手がかりとなります。しかし、数千の要素からテキストを抽出するために都度CDP通信を発生させると、パフォーマンスが著しく低下します。<br>
この問題に対し、本エンジンでは **W3C標準のDOM仕様である「テキストノード（nodeType = 3）」を直接解析する** アプローチで解決しました。CDPの **DOMSnapshot** が一度の通信で取得するフラットな配列内にある全テキストデータを、展開処理（**Convert-DomSnapshotFlat**）の内部で直接親要素へ結合。追加の通信負荷を一切かけることなく、全要素へのテキスト情報付与に成功しています。

🛠️ **5. 座標逆引き「PointReverse」がもたらすフェイルセーフ**<br>
モダンなWebアプリでは、「虫眼鏡アイコンだけの検索ボタン（SVG画像のみ）」やハンバーガーメニューなど、テキスト情報を一切持たない要素が多々あります。<br>
本エンジンでは、普段は堅牢なCSSセレクタを生成する **Fuzzy検索ルート** を常用しつつ、テキストが存在しない難敵や特殊なフレームワークに遭遇した際は、**PointReverse機能（座標逆引きルート）** へ切り替えることが可能です。マウスの物理的な位置から要素を直接特定することで、柔軟なフェイルセーフを実現しています。

⚙️ **技術ハイライト:** OS・ブラウザ間の座標統合メカニズム<br>

本エンジン最大の強みは、ピッカーによる要素取得やJSエラー時の物理操作フォールバックにおいて、**「OSの世界」と「ブラウザの世界」をミリ秒単位で正確に行き来する座標変換処理** です。

📌 **座標系とDPRの前提知識**<br>

* **Screen座標（OS絶対座標）:** モニター全体の左上を起点とする物理ピクセル。マウスの移動や物理クリックで使用します。
* **Client座標（ウィンドウ相対座標）:** WebView2コントロールの左上を起点とする座標。
* **DPR（Device Pixel Ratio）:** Windowsの「ディスプレイの拡大率（125%など）」。これがOSの物理ピクセルとブラウザの論理ピクセルのズレを生む根本原因です。

> 🚧 **iframeを越える：絶対座標と相対座標の制御**<br>
> 業務システムに多用される多段iframeは、RPA開発において「座標ズレの温床」となります。CDPの **DOM.getBoxModel** は親ウィンドウを基準とした「絶対座標」を返すのに対し、JavaScriptの **getBoundingClientRect** はiframe内部を基準とした「相対座標」を返します。
> 
> この仕様差異に対し、本エンジンは **「操作の主軸をJavaScriptによるDOM操作に置き、物理座標はフォールバック専用と割り切る」** ハイブリッド設計を採用しています。標準コマンドは **el.click()** 等のJS操作を主軸とするため、座標ズレを無視して確実な動作が可能です。
> 
> 一方で、JS操作がシステムに拒絶される特殊なUIに対しては、CDPが取得した絶対座標を用いてシームレスに物理クリックへフォールバックします。さらに、CORS（クロスドメイン）制約等で正確な座標取得が困難なiframe内要素に対しては、**「手動補正用の警告フラグ」を立てて運用カバーを促す** というフェイルセーフも備えています。

🔄 **パターンA: 【ピッカー実行時】 OS座標からDOM要素を逆引きする** (PointReverse)<br>
※ 本エンジン内部で自動処理されるプロセスです。画面上の要素にマウスを合わせた際、その物理的な位置からブラウザ内のDOM要素を特定します。

1. **OS座標の取得:** UIAから要素の中心の絶対物理座標（Screen X/Y）を取得します。
2. **Client座標への変換:** **PointToClient** メソッドを使用し、ブラウザウィンドウ内での相対物理座標（Client X/Y）に変換します。
3. **ブラウザ論理座標への変換（DPRとスクロール補正）:** 取得した Client X/Y を **DPRで除算** して論理ピクセルに戻し、さらにページのスクロール量（scrollX/Y）を加算します。
*(計算式: **uiaCenterX = (clientX / dpr) + scrollX**)*
4. **DOMとの照合:** この計算結果と、CDP(**DOMSnapshot**) で取得済みの正確な **BoundingBox** 座標を比較し、ユークリッド距離とアクセシビリティ属性から最も一致する要素を特定します。

👊 **パターンB:** 【操作フォールバック時】 DOM座標からOS物理クリックを実行する<br>
※ JavaScriptでの操作（**.click()** 等）がSPAのイベントフック等により拒絶される強固な要素に対し、エンジンが自動でマウスカーソルを移動させて物理操作を行う流れです。

1. **論理座標の取得:** DOMから対象要素の **BoundingBox**（絶対論理座標）を取得します。
2. **スクロール量の減算:** 絶対論理座標から現在のスクロール量を引き、画面内での見え方（Client論理座標）を算出します。
3. **物理座標への変換（DPRの乗算）:** 算出した論理座標に **DPRを乗算** し、OSが認識できる物理的な Client X/Y に変換します。
4. **Screen座標への変換:** **PointToScreen** メソッドを使用して、モニター上の絶対物理座標（Screen X/Y）に変換します。
5. **物理クリックの実行:** 算出した Screen X/Y に対して、Win32 API (**SetCursorPos** と **mouse\_event**) を用いて強制的にマウスクリックを発火させます。

**補足**<br>
**● C列・D列 への座標登録**（ピッカー I列・J列から）<br>

_○ 絶対座標（Client X, Client Y）の算出ステップ_<br>
**STEP 1 (対象取得)：** ピッカーで対象要素の boundingBox（枠情報：x, y, width, height）を取得する。<br>
**STEP 2 (中心算出)：** 要素の左上座標（x, y）に幅・高さの半分を足し、要素の中心論理座標を求める。<br>
**STEP 3 (座標変換)：** 算出した論理座標にディスプレイの DPR（例：1.25）を掛け、ブラウザ描画エリア左上を起点とした絶対座標（Client X, Client Y）に変換する。

**A. ケース1** （https: //ja.wikipedia.org/wiki）: _**成功**_
```text
  PS_STDOUT: [LOG] <2026-10,,,> <Info> [PointReverse] Screen(X=943, Y=70) -> Client(X=943, Y=41)
  PS_STDOUT: [LOG] <2026-10,,,> <Success> [RUN 1/3]: [OK] tag=BUTTON, id=, name= ,[left=729, top=17, width=52, height=32]
    * **ログの取得座標:** Client(X=943, Y=41) （ブラウザ左上からの相対ピクセル）
    * **要素の論理座標 (BoundingBox):** x:729, y:17, width:52, height:32
    * **VBAでの出力 (I, J列):**
        中心 X = (729 + 52 / 2) × DPR(1.25) = 755 × 1.25 = 943.75 → I列: 944
        中心 Y = ( 17 + 32 / 2) × DPR(1.25) =  33 × 1.25 =  41.25 → J列:  41
```

**B. ケース2** （https: //the-internet.herokuapp.com/iframe）: _**大きくズレる**_
```text
  PS_STDOUT: [LOG] <2026-10,,,> <Info> [PointReverse] Screen(X=960, Y=272) -> Client(X=960, Y=243)
  PS_STDOUT: [LOG] <2026-10,,,> <Success> [RUN 1/3]: [OK] tag=P, id=, name= ,[left=16, top=16, width=937, height=22]
    * **ログの取得座標:** Client(X=960, Y=243)
    * **要素の論理座標 (BoundingBox):** x:16, y:16, width:937, height:22
    * **VBAでの出力 (I, J列):**
        中心 X = (16 + 937 / 2) × 1.25 = 605.6  → I列: 606
        中心 Y = (16 +  22 / 2) × 1.25 =  33.75 → J列:  34
```

**【原因】** getBoundingClientRect() は、「対象要素が属している Document（ここでは iframe の内部の窓）」の左上を X=0, Y=0 として座標を返します。そのため、VBA側で計算された 
 I, J列 は、画面全体から見た座標ではなく、「iframeの枠の左上から測った相対座標」になってしまっています。<br>

**【対応】** iframe（インラインフレーム）内要素の座標に関する制約<br>
iframe内の要素は、boundingBox が「iframe枠の左上を起点(0,0)とした相対座標」を返すブラウザ仕様としたため、画面全体の絶対座標へ逆算することは困難なため、複雑な座標補正を諦め、そのままの相対値で算出します（ **I, J列 の値はズレます** ）。ピッカー取得時、iframe内要素であれば要素を薄黄色でハイライトし、K列に 「*Frame要素」 と表示します。<br>
自動テストの C列・D列 に座標を登録する際は、取得ログに出力される `Client(X=..., Y=...)` の値を直接記入するか、手動で補正してください。<br>
（要素のクリックや入力は「CSSセレクタ（またはXPath）」を用いたJS操作が主軸で、座標（BoundingBox）を使うのはあくまで「JS操作が失敗したときの物理クリック用フォールバック」です。）

<details>
  <summary>👉 <i><b>● 座標情報（BoundingBox）の活用場面</b>（JS操作が効かないケース）</i></summary>

* セキュリティ機能で「JS操作をブロックしている」サイト
ログイン画面、一部のSaaSなど、ボットによる不正操作を防ぐため、「OSレベルの物理的なマウスクリックやキー入力」しか受け付けないように制御されているサイト。 JSで element.click() と命令しても、システム側が「人間によるクリックではない」と判定して無視してしまうケース。<br>
👉 取得した座標に対して **Invoke-DesktopCoordinateClick** （マウスポインタを物理的に移動させてクリック）を試す。

* モダンWebフレームワーク（React, Vueなど）の複雑な入力フォーム
テキストボックスにJSで無理やり element.value = "テスト" と値を書き込んでも、裏側のシステム（内部ステート）が更新されず、保存ボタンを押すと空欄に戻ってしまう現象。<br>
👉 座標をクリックしてフォーカスを当て、キーボードから物理的に文字を送信する（ **Invoke-DesktopSendKeys** ）」という人間と同じ手順を踏む。<br>

* DOMツリーを持たない「一枚絵」のコンポーネント操作。(HTML要素として分解できないもの) <br>
  ・ Canvas要素: お絵かきツールや、グラフ・チャートの内部。<br>
  ・ 地図アプリ: Googleマップのような、ドラッグ可能な巨大な画像領域。<br>
  ・ PDFビューア: ブラウザ内で開いたPDFの特定位置のクリック。<br>
👉 「その要素の中心から右に○○pxの位置をクリックする」といった座標ベースの相対操作。

* ブラウザ外（OSの機能）とのシームレスな連携<br>
ファイルのアップロードやダウンロード時などに、ブラウザの制御を離れてWindows OS標準の「ファイル選択ダイアログ」が表示される。<br>
👉 このダイアログはWebのDOMではないため、デスクトップUIAでの操作や、座標ベースでの物理クリック・キー送信が必要。
</details>

**● (物理Input)、(物理Click)、(RobustDOM) テスト** <br>
本エンジンでは、要素ピッカーが取得した情報を元に、通常のDOM操作が失敗した場合でも確実な操作を担保するための「フォールバック機構」を備えています。<br>
ここでは、自動テストのログを通じて、「物理操作へのフォールバック時の座標変換」と、「曖昧な指定から確実な要素を特定するRobustDOM機能」について補足します。

```vba
        responseStr = rpaEngine.RunAction("Test-WebPointReverse", CreateParams("ClientX", cX, "ClientY", cY))
        レスポンスから "boundingBox":{...} のJSON部分を取得する。
```

👉 **テスト1 & 2：** 物理操作へのフォールバック (物理Input / 物理Click)<br>
このテストでは、わざと存在しない無効なセレクタ（`fakeSelector = #not_exist_...`）をエンジンに渡し、DOM経由の操作を故意に失敗させます。要素が見つからない場合、エンジンはピッカーから渡された **boundingBox**（絶対論理座標）を利用し、OSレベルのマウス・キーボード操作へと自動的に切り替わります。

```vba
' 無効なセレクタを意図的に設定してフォールバックを誘発
Dim fakeSelector As String: fakeSelector = "#not_exist_173647"

' テスト1: 物理Input (Yahoo 路線情報 / 出発駅)
fallbackRes = rpaEngine.RunAction("Set-WebTextInput", CreateParams( _
    "Selector", fakeSelector, "Value", "Fallback OK!", "BoundingBox", bboxJson))

' テスト2: 物理Click (Yahoo 路線情報 / 検索ボタン)
fallbackRes = rpaEngine.RunAction("Invoke-WebClick", CreateParams( _
    "Selector", fakeSelector, "BoundingBox", bboxJson))
```

> [!NOTE]
> **ログを見たときの「座標ズレ」**
> VBA側からテスト用に渡した **ClientY**（例: 529）と、ログに出力された物理クリックのY座標（558）を見比べると、+29 のズレが生じているように見えます。これは計算のバグではなく、「座標の基準（原点）の違い」による正常な変換結果です。

* **VBA側の ClientY (529)** <br>
ブラウザの描画領域（WebView2コントロール）の左上を原点 (0,0) とした「相対座標」です。
* **物理クリック時の Y (558)** <br>
Windows OSのディスプレイ画面の左上を原点 (0,0) とした「絶対スクリーン座標」です。

内部関数 **Convert-BoundingBoxToScreenPoint** では、以下の処理を行い、論理座標をOSの物理座標へ変換しています。
* **スクロール補正:** ページ最上部からの絶対座標 (boundingBox) から現在のスクロール量を減算。
* **中心点の算出:** 要素の左上ではなく、中央を正確に狙う。
* **DPRの計算:** OSのディスプレイ拡大率（125%など）を掛け合わせて物理ピクセルへ変換。
* **ウィンドウ枠のオフセット:** （これが +29 の正体です）OS画面上におけるブラウザの位置や、タイトルバーなどのUI部分の高さを加算。

この変換プロセスにより、ピッカー取得時と画面のスクロール位置が変わっていても、確実に対象要素のど真ん中を物理クリックすることが可能です。

**Get-WebCssSelectorHint** および **Invoke-WebSafeClick** は以下の堅牢な手順を踏みます。

* **可視状態の判定 (isVisible):** getBoundingClientRect() のサイズが0ではないか、display: none や opacity: 0 になっていないかを解析し、「人間が実際にクリックできる要素（候補2）」だけを特定します。
* **自動スクロール:** 要素が画面外にある場合、クリック前に自動で画面中央へスクロール（scrollIntoView）します。
* **ネイティブクリック:** JSによる強制発火ではなく、ブラウザ本来のネイティブなクリックイベントをシミュレートし、SPA（React/Vue等）でのイベント不発を防ぎます。
